# Build Prompt — Airport360 (ZACL Digital Transformation Platform)

You are a senior full-stack engineer and AI/ML engineer. Build a modular digital-transformation platform for an airport operator, in the phased order below.

---

## 0. Context — read this before anything else

This platform is scoped against a real partnership model: an airport authority (operating multiple airport sites, not just one) has signed an MOU with a university to design, develop, and deploy a locally-built ERP system, rolled out in phases. The publicly committed **Phase 1 scope is HR, Procurement, Finance, Business Intelligence, and Capacity Building** — not crowd analytics or AI prediction modules. Stated goals across the partnership: innovation, automation, business intelligence, AI, institutional capacity building, and systems integration, with an explicit emphasis on the solution being locally driven and building local technical capacity, not delivered as an outside black box.

Two hard constraints follow from that:

1. **Build Phase 1 as a genuinely complete, demoable system on its own** — a working multi-site HR/Procurement/Finance/BI system with real capacity-building tracking. Do not treat it as a stub that only makes sense once later phases exist.
2. **Multi-site is a Phase 1 requirement, not a future scaling concern.** The operator runs several airport sites from one head office. Every site-specific record — HR, procurement, finance, and everything added in later phases — must carry a site/`airport_id` reference from the first migration onward. Retrofitting this later is a rewrite, not a patch.

All data in every phase is simulated/anonymized. No real airport databases, restricted systems, biometric databases, or proprietary third-party APIs. No production-certification claims. Every AI/ML output must be visually and textually labeled as a **prototype prediction from simulated data**, with the model's evaluation metric shown alongside it, not just a disclaimer.

---

## 1. Stack (all phases)

**Frontend:** React + Vite + TypeScript + Tailwind CSS + Recharts
**Backend:** Python + FastAPI + SQLAlchemy 2.0 + Pydantic v2 + JWT auth + RBAC enforced at the API layer (not just hidden in the frontend UI — every endpoint independently rejects out-of-role and out-of-site requests with 403)
**Database:** PostgreSQL in production; SQLite for local dev via the same SQLAlchemy models (env-var driven connection string, no code branching)
**Migrations:** Alembic — one migration per schema change, autogenerated from models
**AI/ML:** pandas, NumPy, scikit-learn, OpenCV
**Dev/Ops:** Docker + docker-compose (backend, frontend, postgres — one command boots the whole demo); `.env.example` committed, real `.env` gitignored
**Testing:** pytest + httpx for backend API tests; Vitest + React Testing Library for frontend; one test per API route group minimum, one test per ML module's output shape, one test that explicitly asserts cross-site data isolation

Keep every ML/CV model behind an interface (e.g., `detect(frame) -> BoundingBoxes`, `predict(features) -> QueueForecast`) so it can be swapped for a stronger model later without touching calling code.

---

## 2. Roles (extend across phases, don't replace)

- **Staff** — department-level user; submits requisitions, views own HR record, updates assigned incidents/maintenance tickets in Phase 2
- **Department Head / Approver** — approves requisitions, views department BI
- **Finance Officer** — budget/expense management
- **HR Officer** — staff records, training/capacity-building tracking
- **Operations Manager** (from Phase 2 on) — airport-wide dashboards, monitors queues/incidents/maintenance/baggage, views AI predictions, assigns tasks
- **Administrator** — manages users, roles, sites, system configuration, audit logs
- **Executive / BI Viewer** — cross-site dashboards, read-only
- **Passenger** (from Phase 3 on) — views flight/airport info, reports baggage/facility issues, submits complaints, tracks own reports

---

## 3. Database design (cumulative — build tables as each phase needs them)

**Core / Phase 1:** `sites` (the multi-airport tenant table — every other site-scoped table FKs into this), `users`, `roles`, `employees`, `training_records`, `capacity_building_activities`, `purchase_requisitions`, `purchase_orders`, `vendors`, `budgets`, `expenses`, `audit_logs`

**Phase 2 additions:** `flights`, `passengers`, `baggage`, `baggage_scans`, `queues`, `queue_predictions`, `incidents`, `maintenance_requests`, `cargo_shipments`, `facilities`, `alerts`, `model_runs` (model name, version, trained_at, evaluation metrics — so every prediction can reference which model version produced it, which is what makes an "accuracy: X%" claim on screen auditable)

**Phase 3 additions:** `complaints`, passenger-facing report tables reuse the Phase 2 `incidents`/`maintenance_requests` tables rather than duplicating them — a passenger-reported issue and a staff-reported issue are the same record type

**Phase 4 additions:** `booking_referrals` (affiliate click/redirect tracking — no PNR or payment data stored, since booking itself happens on the airline's own checkout), `travel_agency_partners`

Rules that apply to every table added in every phase:
- Explicit FK relationships with defined cascade behavior
- Index every FK and every column used in dashboard filtering (timestamp, status, severity, site)
- Every site-scoped table carries `site_id → sites.id`

Seed each phase with realistic simulated data across at least two sites, with enough history (1–2 weeks minimum for anything ML touches) that trends and predictions have something real to compute against.

## 4. Phase 1 — Core ERP (build and fully demo this before starting Phase 2)

### 4.1 Human Resources
Employee records (role, department, site, employment status), attendance/leave tracking, basic org-chart/reporting-line structure per site, training/capacity-building record tracking.

### 4.2 Procurement
Purchase requisitions → approval workflow → purchase orders → receipt/fulfillment. Vendor records. Budget-line tagging so spend rolls up into Finance and BI. Site-aware approval routing (a requisition at one site shouldn't route through another site's approval chain unless the org chart says so).

### 4.3 Finance
Budget tracking by department and site, expense recording tied to procurement, basic financial reporting (spend by category/site/period). **No payment processing or PCI scope in this module** — internal record-keeping only; keep that boundary explicit in code comments and docs.

### 4.4 Business Intelligence
Cross-module dashboards: HR headcount/training trends, procurement spend trends, budget-vs-actual finance views, per-site rollups plus an org-wide aggregate. This is where the MOU's "AI" language should first land in something low-risk and legible — e.g., a rule-based anomaly flag on unusual procurement spend — not a black-box model, since this dashboard is likely what gets shown to non-technical stakeholders first.

### 4.5 Capacity Building tracking
Its own module, not folded into HR, since it's named explicitly in the source MOU: track who (students/staff) worked on which part of the platform, what training/certifications were completed, and site-level training program status. This module doubles as a reporting tool for the partnership's own progress reviews.

**Phase 1 exit criteria:** a user can log in, get correctly scoped to their role and site, submit and approve a requisition end-to-end through the real API, see it reflected in Finance and BI dashboards with no hardcoded numbers, and an Administrator can view the audit log of that entire flow.

## 5. Phase 2 — Operational Intelligence layer

### 5.1 Operations Command Center dashboard
Current passenger count, queue lengths, average wait time, active incidents, open maintenance issues, baggage exceptions, cargo in processing, arrivals/departures, and an operational risk level (LOW/MEDIUM/HIGH/CRITICAL) computed from a documented rule, not hardcoded. Include an event timeline merging incidents, alerts, and status changes — this is what makes the Section 10 demo scenario legible to a viewer.

### 5.2 Computer vision (privacy-preserving crowd/queue analysis)
Do **not** build facial recognition or identify individuals. Use OpenCV with a lightweight pretrained person-detection model (HOG+SVM baseline, swappable for a pretrained YOLO/MobileNet-SSD person-class-only detector). Output per processed clip: people detected, estimated queue length, occupancy %, density level, movement direction (optical flow/centroid tracking, aggregate only). **Data retention rule:** only aggregate metrics persist to the DB; uploaded video/frames are processed in-memory or a temp dir and deleted after processing — never stored long-term, never linked to a passenger record.

### 5.3 Queue prediction
Train a baseline scikit-learn model (documented choice of algorithm) on simulated historical data: timestamp, flight arrivals/departures, passenger volume, open counters/lanes, processing rate, current queue size. Report and display real evaluation metrics (MAE/RMSE for the regression, accuracy/F1 for congestion classification) on a held-out split — store it in `model_runs` so the UI's "model accuracy: X" claim is backed by an actual number. Every displayed value tagged **Fact**, **Prediction**, or **Recommendation**.

### 5.4 Baggage Intelligence
Track bag ID, passenger reference, flight, origin/destination, scan events, current/expected location, status (Processing/Loaded/Transferring/Arrived/Delivered/Delayed/Missing/Damaged), exception type, risk score. A basic predictive-risk model flags bags likely to be delayed (short transfer time, missing expected scan, high transfer workload) — every risk score labeled "Prototype risk model — not validated against real mishandling data" in the UI itself, not just in docs.

### 5.5 Incident management
Categories: security, medical, fire/emergency, equipment failure, passenger issue, operational disruption, other. Status flow: Reported → Assigned → Investigating → Responding → Resolved → Closed. Escalation as a concrete rule (e.g., "CRITICAL severity unassigned >5 min → auto-notify Operations Manager + log escalation event"). Full audit trail.

### 5.6 Maintenance management
Categories: toilet, water, electricity, lighting, escalator, elevator, HVAC, seating, signage, other. Track location, priority, assigned technician, status, resolution time, cost. Repeat-failure detection as a real query (same facility + same problem type within a rolling window), not a manual tag.

### 5.7 CargoFlow
Workflow: Registered → Arrived → Documentation → Clearance → Inspection → Storage → Released. Analytics: average clearance time, cargo in processing, delayed shipments, bottlenecks, volume by day/week/month.

### 5.8 Alerts
Severity levels LOW/MEDIUM/HIGH/CRITICAL across queue congestion, baggage risk, critical incidents, overdue maintenance, cargo delays, flight disruptions. Deduplicate by tracking state transitions, not re-firing on every polling cycle while a condition persists.

### 5.9 AI Airport Assistant
Answers questions using the platform's own database/analytics only, structurally separating every response into **Fact** / **Prediction** / **Recommendation**. Implement as retrieval-over-structured-data — query the DB/analytics endpoints, feed only that retrieved data into a constrained prompt or template. If an LLM handles phrasing, its context window contains only data actually retrieved for that query — this is what prevents invented statistics, not an instruction not to invent them.

### 5.10 AI recommendations
Rule/data/model-driven only — no arbitrary text generation. Every recommendation traceable to the specific rule and input values that triggered it.

**Phase 2 exit criteria:** the full surge-demo flow in Section 10 runs end-to-end against seeded data with no manual DB edits.

## 6. Phase 3 — Passenger-facing app

Flight search/status, basic wayfinding, baggage-problem reporting, complaints, facility-issue reporting, and status tracking of submitted reports — writing into the same `incidents`/`maintenance_requests` tables Phase 2 staff already use, not a parallel passenger-only copy. No booking or payment functionality in this phase.

**Phase 3 exit criteria:** a passenger-reported facility issue appears in the staff maintenance queue in real time, with the passenger able to see its status update.

---

## 7. Phase 4 — Booking & travel-agency marketplace (furthest out — do not start before Phases 1–3 are real and in front of real users)

Start **affiliate/meta-search only**: search flights across airlines operating at the org's sites, redirect to the airline's own checkout for payment, log a referral. This deliberately avoids IATA/ARC accreditation and PCI-DSS scope. A travel-agency marketplace (certified/security-endorsed partners listed in-app) is a later monetization layer once passenger volume exists worth selling placement against — document it as a roadmap item, don't build it against zero users.

Route by domain, `/v1` prefix, auto-generated OpenAPI docs with real schema descriptions:
`/auth /users /sites /hr /procurement /finance /bi /capacity-building` (Phase 1)
`/flights /passengers /baggage /queues /predictions /incidents /maintenance /cargo /alerts /ai /computer-vision` (Phase 2)
`/complaints` (Phase 3)
`/bookings /travel-partners` (Phase 4)

## 9. Security (all phases)

JWT auth, hashed passwords, API-layer RBAC, input validation, audit logging on all writes (especially HR/Finance/Procurement — standard ERP governance practice, not just a security nicety), env-based secrets, no hardcoded credentials, API rate limiting on auth and public-facing endpoints, CORS explicitly configured (never wildcarded), structured logging with request IDs. **Site isolation:** every authenticated request resolves to exactly one (or an explicitly authorized set of) `site_id`; write an explicit test asserting no query path can return another site's data. No biometric data ever stored.

## 10. Demo scenario (Phase 2, once built)

1. Simulated site in normal operations → 2. trigger a simulated passenger surge → 3. CV module shows rising crowd density on the sample feed → 4. queue prediction model forecasts severe congestion, evaluation-metric-backed → 5. system generates a deduplicated CRITICAL alert → 6. recommendation engine suggests opening a lane, citing the rule that fired → 7. baggage module concurrently flags high-risk transfer bags → 8. Command Center dashboard reflects all of it in one view with the event timeline → 9. AI assistant, asked what's happening and what to prioritize, answers using only real DB/model data with Fact/Prediction/Recommendation separated → 10. Operations Manager assigns a task from the dashboard; Staff resolve it; the status change reflects back on the dashboard and audit log.

## 12. Scope rules (all phases)

Do **not**: connect to real airport/operator systems, access restricted data, implement real biometric ID, store facial recognition data, claim production certification, invent real statistics, present simulated predictions as real forecasts, build a full flight-booking/ticketing engine before Phase 4's affiliate model is proven, or add features purely to inflate the feature count.

Every major AI/ML feature must show: (1) input data, (2) processing/model, (3) output, (4) plain-language explanation, (5) visualization, (6) an explicit simulated-vs-real data label.

Build incrementally in the phase order above, write tests as you go, and document key design decisions — especially model choices and any rule threshold — noting *why*, even when the why is "reasonable prototype default."
